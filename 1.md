# Prompt migliorato per Codex — Pipeline di generazione e verifica automatica di laboratori Kathara

## Pipeline Python per la generazione e verifica automatica di laboratori Kathara

### 0. Ruolo e obiettivo

Devi progettare e implementare, interamente all'interno del workspace corrente, una pipeline Python completa, modulare, testabile e realmente eseguibile da terminale. La pipeline automatizza, per ciascun prompt trovato in `prompts_generates/`, tre fasi: generazione di un laboratorio Kathara, generazione di un file di correzione (`correction.yaml`), esecuzione di `kathara_lab_checker` su quel laboratorio.

Non realizzare uno script dimostrativo: realizza un pacchetto Python con separazione netta delle responsabilità, tipizzato, coperto da test automatici con `pytest`.

Se durante l'implementazione incontri un'ambiguità che i file reali del workspace, la documentazione locale o l'output di `--help` dei comandi non permettono di risolvere con certezza, non fermarti in attesa di conferma umana (l'esecuzione è non interattiva): scegli l'interpretazione più coerente con i principi di questo prompt, documentala esplicitamente nel README e nel messaggio finale, e prosegui.

### 1. Principi guida (validi per l'intero progetto)

Questi principi sono trasversali e non vengono ripetuti altrove nel dettaglio:

- **Priorità delle fonti di verità.** Prima di assumere nomi di file, opzioni CLI, chiavi di configurazione o struttura di uno schema, ispeziona i file realmente presenti nel workspace (`prompts_generates/`, `kathara-lab-checker/`) e consulta l'output di `--help` o la documentazione locale dei comandi (`codex`, `kathara`, `kathara_lab_checker`). I file reali e l'output reale dei comandi prevalgono sempre sulle ipotesi contenute in questo prompt. Non inventare opzioni CLI, chiavi YAML o campi di schema che non trovi in queste fonti.
- **Nessuna riparazione automatica.** La pipeline non corregge, non rigenera e non ripara laboratori o file `correction.yaml` sulla base dei risultati dei test. Non implementare tentativi multipli, retry generativi, cartelle `attempts/`, stati o configurazioni di "riparazione". Un laboratorio è generato una sola volta, configurato una sola volta, testato una sola volta.
- **Sequenzialità.** I prompt sono elaborati uno alla volta, in un solo processo, senza thread pool, multiprocessing o esecuzione concorrente. Un job raggiunge uno stato terminale (`passed`, `failed`, `error` o `skipped`) prima che inizi il successivo.
- **Nessun `shell=True`.** Ogni comando esterno (`codex`, `kathara_lab_checker`) è costruito come lista di argomenti e invocato con `subprocess.run(..., shell=False)`. Non costruire comandi tramite concatenazione di stringhe da passare a una shell.
- **Separazione delle fasi.** Generazione del laboratorio, generazione della configurazione ed esecuzione del test sono fasi distinte, ciascuna con il proprio workspace isolato quando è coinvolto Codex, e ciascuna con il proprio insieme di errori gestiti (§14).

### 2. Vincoli tecnici e ambito

- Python 3.11 o superiore.
- Genera i laboratori esclusivamente tramite Codex CLI, invocato in locale con `subprocess` (mai l'SDK Python di OpenAI, mai chiamate dirette alle API OpenAI).
- Non usare mai `--dangerously-bypass-approvals-and-sandbox` né `--yolo`, in nessuna fase.
- Usa type hints in tutto il codice di produzione.
- Dipendenze Python attese in `pyproject.toml`: `pyyaml`, `jsonschema` (quando applicabile, §12), `kathara-lab-checker` come pacchetto importabile, `pytest`. Aggiungi altre dipendenze solo se strettamente necessarie.

### 3. Requisiti fondamentali (R1–R22)

La pipeline deve rispettare tutti i seguenti requisiti, referenziati per numero nel resto del prompt.

1. **R1** — Scritta in Python 3.11+.
2. **R2** — Usa Codex CLI tramite `subprocess`.
3. **R3** — Non usa direttamente le API OpenAI.
4. **R4** — Non usa l'SDK Python OpenAI.
5. **R5** — Non usa `shell=True`.
6. **R6** — Elabora i prompt in modo rigorosamente sequenziale.
7. **R7** — Legge file `.md` e `.txt` da `prompts_generates/`.
8. **R8** — Genera un solo laboratorio per ogni prompt.
9. **R9** — Genera un solo `correction.yaml` per ogni laboratorio.
10. **R10** — Esegue il checker una sola volta per ogni laboratorio.
11. **R11** — Non implementa tentativi automatici di riparazione.
12. **R12** — Non modifica il laboratorio sulla base dei risultati.
13. **R13** — Non modifica `correction.yaml` sulla base dei risultati.
14. **R14** — Se un job termina in stato `failed`, salva il risultato e passa **sempre** al prompt successivo.
15. **R15** — Se un job termina in stato `error`, lo registra e passa al prompt successivo **soltanto quando** `continue_on_error` è attivo; altrimenti la pipeline si interrompe (§14 per la differenza fra `failed` ed `error`).
16. **R16** — Conserva laboratori, configurazioni, report, log e manifest in posizioni separate (§6.3).
17. **R17** — Valida staticamente il laboratorio prima di generare `correction.yaml`.
18. **R18** — Valida `correction.yaml` prima di avviare il checker.
19. **R19** — Crea un riepilogo globale dopo aver elaborato tutti i prompt.
20. **R20** — Supporta una modalità `--dry-run`.
21. **R21** — Protegge ogni operazione distruttiva sui path da path traversal e cancellazioni fuori ambito.
22. **R22** — È testabile con `pytest` tramite mock di `subprocess` (nessuna chiamata reale a Codex, Kathara o Docker nei test).

### 5. Scoperta dei prompt

- Sorgente: tutti i file `.md` e `.txt` presenti direttamente in `prompts_generates/` (non ricorsivo), letti come testo UTF-8.
- Esclusi sempre: file nascosti, directory, file con estensione diversa da `.md`/`.txt`.
- File vuoti (0 byte o solo whitespace dopo strip): non generano un laboratorio. Il job riceve stato `skipped` con motivazione esplicita "prompt vuoto", registrata nel manifest — non è trattato come `error`.
- Un errore di decodifica di un singolo file non blocca l'intera pipeline: marca solo quel job come `error` e prosegui.
- Ordinamento naturale e deterministico: spezza i nomi file in sequenze di cifre e sequenze di non-cifre; le sequenze di cifre si confrontano numericamente, le altre lessicograficamente; a parità di chiave naturale, usa il confronto lessicografico puro del nome file come tie-break, per garantire un ordine totale e riproducibile. Esempio: `lab-001-v1.md`, `lab-002-v1.md`, `lab-010-v1.md` devono risultare in quest'ordine.
- La lista completa dei prompt è costruita una sola volta, all'inizio, e poi percorsa in ordine, un prompt alla volta (§1).

### 6. Identificativo del laboratorio, sicurezza dei path e layout dei dati

**6.1 `lab-id`.** Deriva `lab-id` dal nome del file prompt (es. `prompts_generates/lab-001-v1.md` → `lab-001-v1`). Sanitizza impedendo: path traversal, slash e backslash, caratteri di controllo, nomi vuoti, nomi riservati dal sistema operativo, riferimenti a directory superiori. Se la sanitizzazione produce una collisione fra due o più prompt distinti, la pipeline **non** disambigua automaticamente: il preflight fallisce, elenca i file in collisione e la pipeline non elabora alcun prompt finché il conflitto non è risolto manualmente.

**6.2 Sicurezza dei path.** Crea in `paths.py` una funzione centralizzata usata da **ogni** operazione distruttiva (in particolare `shutil.rmtree`). Deve: risolvere il path (`Path.resolve()`) prima di ogni confronto; verificare che il path risolto sia contenuto in `kathara-lab-generates/` (con un confronto tipo `is_relative_to`, non un confronto di stringhe grezzo); rifiutare path uguali o superiori alla root del progetto, alla home utente o a `/`; rifiutare path che escono da `kathara-lab-generates/` tramite `..`; rifiutare symlink che puntano fuori da `kathara-lab-generates/`; rifiutare qualunque richiesta di cancellare `kathara-lab-generates/` nella sua interezza. Nessun altro modulo chiama `shutil.rmtree` direttamente.

**6.3 Layout dei dati per ciascun job.** Definisci `JOB_DIR = kathara-lab-generates/<lab-id>/`:

```
JOB_DIR/
├── prompt.md
├── source/                        # laboratorio generato da Codex, mai eseguito direttamente
├── correction/
│   └── correction.yaml            # input del checker, non un suo output
├── checker-run/
│   └── labs/
│       └── candidate/             # copia di source/ usata solo per il test
├── reports/
│   └── result-summary.json        # + copia organizzata dei report del checker
├── logs/
│   ├── codex-lab.jsonl
│   ├── codex-lab.stderr.log
│   ├── codex-correction.jsonl
│   ├── codex-correction.stderr.log
│   ├── checker.stdout.log
│   └── checker.stderr.log
└── manifest.json
```

Il checker non viene mai eseguito direttamente su `source/`, perché può scrivere file al suo interno; per questo esiste `checker-run/labs/candidate/` (§13). Nel manifest conserva almeno: nome e path originali del prompt, hash SHA-256 del suo contenuto, `lab-id`, timestamp di inizio/fine, durata, versione della pipeline (es. da `__version__` del pacchetto o da `pyproject.toml`), stato finale, esito dei test, hash SHA-256 di `correction.yaml`.

### 7. Flusso obbligatorio per ciascun prompt

Il flusso, identico per ogni prompt e non modificabile nell'ordine, è:

```
1. scoperta del prompt
2. creazione del job (lab-id, JOB_DIR, manifest iniziale con stato "discovered")
3. generazione del laboratorio (Codex, §9)
4. validazione statica del laboratorio (§10)
5. generazione di correction.yaml (Codex, §11)
6. validazione sintattica, strutturale e semantica del YAML (§12)
7. copia del laboratorio nella directory di esecuzione del checker (§13)
8. esecuzione singola di kathara_lab_checker (§13)
9. analisi dei report (§14)
10. salvataggio del risultato (§14, §15)
11. aggiornamento del manifest (§15)
12. passaggio al prompt successivo
```

Non aggiungere fasi di rigenerazione, correzione automatica, retry generativi, tentativi multipli, loop di riparazione, modifica dei test dopo il fallimento, o esecuzione concorrente di più prompt (§1).

### 8. Preflight

Prima di elaborare qualunque prompt, verifica e blocca l'avvio con un messaggio comprensibile se manca un requisito indispensabile:

- Python ≥ 3.11 in uso.
- Esistenza ed eseguibilità del comando `codex`; stato di autenticazione verificato (es. tramite `codex doctor` o `codex login status`, se disponibili nella versione installata, altrimenti secondo la documentazione locale).
- Esistenza di `prompts_generates/` e leggibilità dei suoi file.
- Esistenza di `kathara-lab-checker/` (la cartella di risorse locali: Skill, schema, esempi — distinta dal pacchetto Python `kathara_lab_checker`, installato via pip e invocato con `-m`).
- Individuazione della Skill e del config schema dentro `kathara-lab-checker/` (§10.1).
- Importabilità del modulo `kathara_lab_checker` nell'interprete corrente (`sys.executable`), e verifica che la versione installata supporti configurazioni in formato YAML e non solo JSON — controllalo da metadati del pacchetto o dalla documentazione/changelog locale, non darlo per scontato.
- Importabilità di `yaml`; importabilità di `jsonschema` se il config schema individuato è un JSON Schema (§12).
- Disponibilità del comando `kathara` e del motore di container sottostante (tipicamente Docker): verificane la presenza senza assumere un nome fisso.
- Possibilità di creare file in `kathara-lab-generates/`.
- Assenza di collisioni fra gli identificativi generati (§6.1) — un conflitto blocca l'avvio.
- (Opzionale, consigliato ma non vincolante) rilevamento di un'eventuale esecuzione concorrente della pipeline stessa, ad esempio tramite un semplice file di lock in `kathara-lab-generates/`, per evitare corruzioni del manifest se la pipeline viene lanciata due volte per errore.

In modalità `--dry-run` (§18), i controlli di disponibilità di strumenti esterni (`codex`, Kathara) sono soltanto avvisi non bloccanti, perché nessuno strumento esterno viene realmente invocato; i controlli su path, permessi e validità della configurazione restano invece bloccanti, perché servono a calcolare un piano accurato.

### 9. Generazione del laboratorio (Codex)

Per ogni prompt crea un workspace isolato ed effimero, popolato solo con:

```
input/
└── prompt.md
output/
└── lab/
```

Istruisci Codex esplicitamente a: leggere solo `input/prompt.md`; non leggere altri prompt né laboratori generati in precedenza; generare l'intero laboratorio dentro `output/lab/`; non creare file fuori dal workspace; non generare ancora `correction.yaml`; non modificare il prompt; verificare la coerenza tra `lab.conf`, interfacce, file `.startup`, routing e servizi; produrre una soluzione completa, senza placeholder e senza limitarsi a uno scaffold; non avviare il checker.

Al termine, copia `output/lab/` in `JOB_DIR/source/`, poi elimina (o archivia sotto un'eventuale cartella di debug, se è attiva una modalità verbosa) il workspace isolato: non fa parte del layout canonico del job.

**9.1 Esecuzione di `codex exec`.** Realizza una classe `CodexRunner` che costruisce il comando come lista di argomenti. Punto di partenza, da verificare e adattare:

```python
command = [
    "codex", "exec",
    "--sandbox", "workspace-write",
    "--cd", str(workspace),
    "--json",
    "--output-last-message", str(summary_path),
    "--ephemeral",
    instruction,
]
result = subprocess.run(
    command,
    shell=False,
    capture_output=True,
    text=True,
    encoding="utf-8",
    errors="replace",
    timeout=timeout_seconds,
)
```

Prima di considerare definitiva questa implementazione, esegui `codex exec --help` (e se necessario `codex --help`) per confermare che i flag sopra siano effettivamente accettati, nella posizione indicata, dalla versione installata: il supporto e la sintassi di flag come quello di approvazione automatica variano tra versioni di Codex CLI, e la documentazione può risultare disallineata dal comportamento reale. Se `codex exec` nella versione installata non richiede o non accetta un flag di approvazione esplicito (perché per definizione non è interattivo), non aggiungerlo; se invece lo richiede, usa esattamente la sintassi che `--help` mostra; se la CLI non accetta il flag direttamente dopo `exec` ma la funzionalità resta configurabile, usa un override di configurazione (es. `-c approval_policy=...` o un profilo dedicato) invece di indovinare una sintassi non confermata. In nessun caso sostituiscilo con `--dangerously-bypass-approvals-and-sandbox` o `--yolo` (§2). Non introdurre altri flag non confermati da `--help` o dalla documentazione locale.

Cattura e salva separatamente: stdout, stderr, return code, durata misurata dalla pipeline, eventuale timeout, il comando eseguito con eventuali segreti rimossi. Interpreta lo stream JSONL riga per riga: righe malformate vengono registrate e ignorate singolarmente; se non viene mai prodotto un evento di completamento valido, tratta il job come errore tecnico.

Gestisci esplicitamente, come errori tecnici distinti: comando `codex` non trovato; autenticazione assente o scaduta; timeout (`subprocess.TimeoutExpired`); return code diverso da zero; output JSONL malformato; processo terminato in modo anomalo; messaggio finale o cartella di output mancanti; file prodotti fuori dalla directory autorizzata del workspace.

### 10. Validazione statica del laboratorio

Applicala a `JOB_DIR/source/`, prima di generare `correction.yaml`. Verifica almeno: presenza di `lab.conf`; file regolari e leggibili; assenza di symlink che escono dal workspace; assenza di path assoluti; nomi dei dispositivi coerenti fra `lab.conf` e i file generati; presenza dei file `.startup` richiesti; assenza di cartelle vuote; assenza di placeholder o testo tipo `TODO`, `CHANGE_ME`, `INSERT_HERE`; assenza di un secondo laboratorio annidato per errore; presenza degli eventuali file di configurazione richiesti esplicitamente dal prompt originale.

Questa validazione non sostituisce il checker: serve solo a bloccare output evidentemente incompleti o inutilizzabili. Se fallisce: registra gli errori, imposta lo stato del job su `error`, non generare `correction.yaml`, non eseguire il checker, non chiedere a Codex di correggere il laboratorio, e passa al prompt successivo se `continue_on_error` è attivo (§14).

**10.1 Individuazione della Skill e del config schema.** Cerca dentro `kathara-lab-checker/`, in quest'ordine: prima un file chiamato esattamente `SKILL.md` (case-insensitive) e uno chiamato esattamente `config-schema.json`; se uno dei due non esiste con quel nome, cerca un unico file `.md` (per la Skill, escludendo `README.md`) o un unico file `.json`/`.yaml`/`.yml` (per lo schema) nella stessa cartella. Se trovi più candidati plausibili per lo stesso ruolo e nessuno corrisponde al nome convenzionale, non indovinare: il preflight fallisce elencando i candidati trovati. Un'eventuale cartella `examples/` è materiale di riferimento che Codex può leggere ma non deve copiare letteralmente dentro `correction.yaml`.

### 11. Generazione di `correction.yaml` (Codex)

`correction.yaml` è un **input** del checker, non un report da esso prodotto. Va generato a partire da: il prompt originale, il laboratorio in `source/`, la Skill e il config schema individuati (§10.1). Va salvato in `JOB_DIR/correction/correction.yaml`, con questa estensione esatta — mai `.yalm`.

Crea un secondo workspace isolato ed effimero (distinto da quello di §9), popolato con:

```
input/
├── prompt.md
└── lab/                    # copia di JOB_DIR/source/
resources/
├── SKILL.md                # nome reale individuato in §10.1
├── config-schema.json      # nome reale individuato in §10.1
└── examples/                # se presente
output/
└── correction.yaml
```

Istruisci Codex a: leggere per intero Skill, schema e prompt originale; analizzare il laboratorio generato usandolo come fonte delle scelte implementative effettive, senza però omettere un requisito del prompt solo perché il laboratorio non lo implementa correttamente; generare esclusivamente `output/correction.yaml`, senza commenti o spiegazioni nel corpo del file; non usare path assoluti; usare `lab_inline` per la struttura del laboratorio ogni volta che questo evita di dipendere da un path esterno assoluto; includere soltanto controlli realmente supportati dalla Skill e dallo schema individuati, senza inventarne di non supportati né di non verificabili dal checker; non modificare il laboratorio; non avviare il checker; non creare alcun file diverso da `correction.yaml`.

Copia il file da `output/correction.yaml` a `JOB_DIR/correction/correction.yaml` (Codex non scrive mai direttamente in quest'ultima directory), poi rimuovi il workspace isolato con la stessa logica di ciclo di vita di §9.

`correction.yaml` è usato una sola volta per il test e non viene mai modificato dopo aver visto i risultati, né per farli passare né per qualunque altro motivo. Dopo la validazione (§12) calcola e registra nel manifest il suo hash SHA-256; il checker deve operare esattamente sul file che ha superato la validazione.

### 12. Validazione di `correction.yaml` (tre livelli)

Se un qualunque livello fallisce: registra tutti gli errori trovati, imposta lo stato del job su `error`, non avviare il checker, non tentare di rigenerare il file, passa al prompt successivo se `continue_on_error` è attivo.

**Livello 1 — Sintassi.** Usa esclusivamente `yaml.safe_load()` (mai loader non sicuri). Il documento deve produrre un mapping; se produce una stringa, una lista, `None`, più documenti concatenati o un oggetto non standard, la validazione fallisce. Come misura precauzionale, valuta di limitare la dimensione massima del documento e la profondità di eventuali ancore/alias prima del parsing: `yaml.safe_load()` esclude l'esecuzione di codice arbitrario, ma non protegge da un'espansione eccessiva di ancore molto annidate.

**Livello 2 — Schema.** Se il file individuato in §10.1 è un vero JSON Schema (es. presenza di `$schema`, oppure struttura con `type`/`properties` coerente con le convenzioni JSON Schema), validalo con `jsonschema`, riportando per ogni errore: percorso del campo, valore non valido, regola violata, messaggio dello schema. Se il file non è un JSON Schema riconoscibile, implementa invece una validazione strutturale diretta guidata dai campi effettivamente documentati nello schema/Skill trovati, registrando esplicitamente nei log quale delle due modalità è stata usata.

**Livello 3 — Semantica.** Deriva l'elenco autoritativo dei controlli dallo schema/Skill realmente trovati: l'elenco seguente (basato sui campi tipici di `kathara-lab-checker`, come `structure`, `lab_inline`, `requiring_startup`, `ip_mapping`, `labs_path`, `convergence_time`, `default_image`) è un punto di partenza, non un tetto né un pavimento fisso — aggiungi controlli per concetti che lo schema reale definisce anche se non elencati qui, e non inventarne per concetti che lo schema reale non definisce. Verifica almeno: tutti i dispositivi citati esistono nel laboratorio; le interfacce citate appartengono al dispositivo corretto; indirizzi IP e subnet sono formalmente validi e coerenti col laboratorio; assenza di dispositivi duplicati; se presente, `lab_inline` non è vuoto; i dispositivi in `requiring_startup` possiedono il relativo file `.startup`; tutti i path restano dentro il job; assenza di placeholder o chiavi sconosciute rispetto allo schema; assenza di riferimenti a laboratori diversi da quello corrente; plausibilità di gateway/interfacce per le route attese; corrispondenza fra servizi DNS/web/routing citati e dispositivi realmente presenti.

### 13. Preparazione ed esecuzione del checker

**Preparazione.** Elimina in modo sicuro (§6.2) solo l'eventuale precedente `checker-run/` del job corrente; ricrea `checker-run/labs/candidate/`; copia il laboratorio da `source/` a `candidate/` senza seguire symlink esterni; registra l'hash dei file copiati; lascia `source/` intatto. Non toccare mai cartelle esterne al job corrente.

**Esecuzione.** Un solo processo per job, così costruito (verifica con `python3 -m kathara_lab_checker --help` prima di finalizzare, per lo stesso motivo esposto in §9.1):

```python
command = [
    sys.executable,
    "-m", "kathara_lab_checker",
    "--config", str(correction_path),
    "--labs", str(labs_directory),
    "--no-cache",
    "--report-type", "csv",
]
```

Usa `sys.executable`, mai un nome di interprete assunto come `python3`. Cattura stdout, stderr, return code, durata, directory di esecuzione e file prodotti; imposta un timeout configurabile e gestisci esplicitamente `subprocess.TimeoutExpired`. Il fallimento del processo (non avviabile, timeout, terminazione anomala) e il fallimento dei test (processo concluso correttamente ma con esiti negativi) sono due condizioni distinte, classificate rispettivamente come `error` e `failed` (§14).

Il checker non viene mai rieseguito per lo stesso job, per nessun motivo — non quando alcuni test falliscono, non quando i report segnalano problemi di raggiungibilità, route mancanti, DNS o servizi falliti: quell'esito è il risultato finale da registrare, non un segnale per riprovare.

### 14. Classificazione degli esiti

Uno stato per job, determinato così (non basarti solo sul return code del processo checker: analizza sempre anche i report):

- **`passed`** — il checker è stato eseguito ed è terminato correttamente, i report attesi esistono e sono leggibili, e il numero di test falliti è zero.
- **`failed`** — il checker è stato eseguito ed è terminato correttamente, i report sono leggibili, ma almeno un test è fallito. Un job `failed` **non interrompe mai** l'elaborazione dei prompt successivi (R14): è un esito legittimo del test, non un malfunzionamento della pipeline.
- **`error`** — il job non può essere completato per un errore tecnico: Codex non disponibile o non autenticato, timeout, laboratorio non generato, validazione statica fallita, YAML non valido, configurazione non conforme allo schema, checker non avviabile, report mancanti o illeggibili. Un job `error` interrompe la pipeline **solo se** `continue_on_error` è `false`; se è `true`, la pipeline registra l'errore e passa al prompt successivo (R15).
- **`skipped`** — il job non è stato (ri)eseguito perché già completato e invariato secondo le regole di idempotenza (§18), oppure escluso da una regola esplicita (incluso il caso del prompt vuoto, §5). Un job `skipped` conta comunque come "prompt considerato" ai fini del riepilogo globale e della condizione "tutti i prompt elaborati".

Individua i CSV prodotti dal checker senza dipendere da un nome file fisso: cerca ricorsivamente file `*.csv` sia dentro `checker-run/labs/candidate/` (report specifici del laboratorio) sia nella cartella padre `checker-run/labs/` (eventuale report aggregato); classifica ciascun file ispezionandone intestazione/colonne o il nome (es. presenza di "summary", "failed", "all", o del `lab-id`) invece di assumere un prefisso letterale. Se dai CSV trovati non è possibile ricavare in modo affidabile i conteggi dei test, tratta il job come `error` per report mancanti o non interpretabili, invece di indovinare un esito.

Da questi report calcola almeno: `total_tests`, `passed_tests`, `failed_tests`, `pass_percentage`, `failure_categories`, `checker_process_return_code`, `checker_execution_status`, `reports_found`, `reports_missing`.

### 15. Persistenza per singolo job: report, log, manifest

In `JOB_DIR/reports/` copia o riepiloga i report del checker, mantenendo comunque intatti gli originali prodotti in `checker-run/`. Crea `JOB_DIR/reports/result-summary.json`, ad esempio:

```json

  "status": "failed",
  "total_tests": 25,
  "passed_tests": 21,
  "failed_tests": 4,
```

I report sono esclusivamente esiti finali da conservare: non vengono mai riutilizzati per modificare il laboratorio o la configurazione.

Scrivi `manifest.json` in modo atomico (file temporaneo, flush, sostituzione atomica) così che una terminazione improvvisa non lo corrompa mai. Usa il modulo standard `logging`: log generale di pipeline, log per singolo laboratorio, log JSONL di Codex, stdout/stderr del checker, riepilogo finale, traceback completi nei file di log e messaggi sintetici a terminale. Non scrivere mai nei log: token, contenuto di file di autenticazione, credenziali, cookie o altri dati sensibili di Codex.

### 17. Gestione degli errori ed exit code

Definisci eccezioni dedicate almeno per: `PreflightError`, `PromptDiscoveryError`, `CodexExecutionError`, `LabGenerationError`, `LabValidationError`, `CorrectionGenerationError`, `YamlValidationError`, `SchemaValidationError`, `SemanticValidationError`, `CheckerExecutionError`, `ReportParsingError`, `UnsafePathError`, `ManifestError`.

L'orchestratore principale ha una forma equivalente a:

```python
def run_all_prompts() -> PipelineSummary:
    prompts = discover_prompts()
    for prompt in prompts:
        try:
            process_single_prompt(prompt)
        except PipelineJobError as exc:
            record_job_error(prompt, exc)
            logger.exception("Errore durante il job %s", prompt.name)
            if not config.processing.continue_on_error:
                raise
        finally:
            release_job_resources(prompt)
    return build_final_summary()
```

Il programma termina sempre con un exit code coerente con l'esito peggiore riscontrato, con questa priorità (dal più al meno grave): `3` se il preflight o la configurazione hanno impedito l'avvio; altrimenti `2` se almeno un job è in `error`; altrimenti `1` se almeno un job è `failed`; altrimenti `0` (tutti `passed` o `skipped`). Documenta questa scelta nel README.

### 18. Idempotenza, `--force` e `--dry-run`

**Idempotenza.** Quando `processing.skip_completed` è attivo (default), calcola l'hash del prompt: se esiste già un job con stesso hash del prompt, stessa versione della pipeline, stesso hash dello schema, stesso hash della Skill, stato finale `passed` o `failed`, e report completi e leggibili, il job viene marcato/lasciato `skipped` e non rieseguito, salvo `--force`. Un job interrotto a metà (terminato in uno stato non terminale per un crash precedente) **non** è considerato completato ai fini di questa regola: alla ripartenza va rieseguito da capo come se fosse il suo primo tentativo, sovrascrivendo gli artefatti parziali — non è una seconda esecuzione di un job già concluso, perché il primo tentativo non aveva mai raggiunto uno stato terminale.

**`--force`.** Disattiva la regola di skip per l'esecuzione corrente: ogni prompt selezionato viene rigenerato e ritestato da zero, sovrascrivendo gli artefatti del job precedente. Resta comunque valido, entro l'esecuzione corrente, il vincolo "una sola volta" (R8–R10).

**`--dry-run`.** Esegue scoperta, ordinamento, derivazione dei `lab-id` e valutazione delle regole di skip, per poter riportare accuratamente cosa verrebbe fatto, ma non produce alcun effetto reale: non avvia Codex, non avvia Kathara o il checker, non crea né cancella directory, non scrive il manifest. Mostra: prompt che sarebbero elaborati e il loro ordine, directory che sarebbero create, i comandi Codex e checker che sarebbero eseguiti per ciascun job non-skippato, e i job che sarebbero saltati con relativa motivazione.

Comandi supportati almeno:

```
python3 main.py run --all
python3 main.py run --prompt lab-001-v1.md
python3 main.py run --all --force
python3 main.py run --all --dry-run
python3 main.py status
python3 main.py validate
python3 main.py preflight
```

### 20. Test automatici (`pytest`)

Nessun test invoca realmente Codex, Kathara o Docker: usa mock di `subprocess`. Copri almeno queste categorie:

- **Scoperta e ordinamento**: ordinamento naturale, esclusione di file non supportati, gestione dei prompt vuoti, determinismo dell'ordine.
- **Sicurezza dei path**: sanitizzazione dei nomi, prevenzione del path traversal, rilevamento delle collisioni, rifiuto di cancellazioni fuori da `kathara-lab-generates/`.
- **Validazione YAML/schema/semantica**: parsing sicuro, validazione JSON Schema (quando applicabile) e validazione strutturale alternativa, ciascun livello di validazione semantica.
- **Integrazione con Codex**: costruzione del comando come lista (mai stringa), gestione di return code diverso da zero, timeout, output JSONL malformato, comando non trovato.
- **Integrazione con il checker**: uso di `sys.executable`, costruzione del comando, gestione del timeout, parsing robusto dei CSV, distinzione fra `failed` ed `error`.
- **Stato e idempotenza**: manifest atomico, comportamento di `--force`, comportamento di `--dry-run`, skip di job già completati, ripresa di job interrotti a metà.
- **Orchestrazione**: un job `failed` porta al prompt successivo; comportamento di `continue_on_error`; elaborazione di tutti i prompt disponibili; generazione del riepilogo globale; verifica (tramite i mock) che Codex sia invocato esattamente una volta per la generazione del laboratorio ed esattamente una volta per la generazione dello YAML, e che il checker sia invocato esattamente una volta per laboratorio; assenza di qualunque logica di riparazione/rigenerazione nel codice.

Crea fixture minime di laboratori Kathara per questi test.

### 22. Criteri di completamento (verificabili)

Il lavoro è completo quando, verificabilmente:

1. `python3 main.py preflight`, `python3 main.py validate` e `python3 main.py run --all --dry-run` terminano con successo su un ambiente correttamente configurato.

3. La suite `pytest` passa e copre tutte le categorie di §20.
4. Il codice non contiene `shell=True` né logica riconducibile a riparazione/rigenerazione automatica (nessun riferimento a retry, repair, attempts nel codice di produzione), e usa type hints.
5. Tutti i requisiti R1–R22 (§3) sono soddisfatti.
6. Il flusso a 12 fasi di §7 è rispettato nell'ordine indicato, verificabile tracciando l'esecuzione di almeno un prompt end-to-end (anche con Codex/checker mockati nei test).
7. Dopo un job `failed`, il prompt successivo viene comunque elaborato.
8. Viene prodotto un riepilogo globale (`pipeline-summary.json` e, se previsto, `.csv`) coerente con lo schema di §16.
9. Un errore su un prompt non compromette gli artefatti già salvati per gli altri prompt.
